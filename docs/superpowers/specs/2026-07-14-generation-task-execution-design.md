# GenerationTask Execution Identity Design

## Goal

Make every Java-to-Worker GenerationTask dispatch durably identifiable after retries and Java restarts, so a Worker result is accepted only when its `messageId`, `taskId`, and `attempt` identify the intended execution.

## Problem

The asynchronous execution and result contracts require `messageId`, but `generation_task` currently stores only its mutable current `attempt`.  A retry overwrites the task's active attempt, and a restart leaves no durable record that associates a callback `messageId` with the execution Java actually dispatched.  This makes the documented stale-callback and idempotency rules impossible to verify reliably.

## Domain model

`GenerationTask` remains the aggregate and current-state projection.  `GenerationTaskExecution` is a durable, immutable-at-creation record for one Worker dispatch of that task.

- An execution is identified by its Java-generated `messageId`.
- A task can have many executions over its lifetime.
- A task and attempt identify at most one execution.
- The `payloadSnapshot` is the immutable `payload` sent in the execution message, not a later reconstruction from mutable project state.
- `attempt` is the canonical term used by the contracts and database; no parallel `attemptNo` field is introduced.

## Persistence

Create `V5__add_generation_task_execution.sql` with a `generation_task_execution` table:

- `message_id uuid primary key` — the contract `messageId` generated by Java.
- `task_id uuid not null` — foreign key to `generation_task(id)`.
- `attempt integer not null` — non-negative execution sequence.
- `trace_id varchar(128)` — trace correlation copied from the dispatch.
- `payload_snapshot jsonb not null` — immutable execution payload.
- `status varchar(16) not null default 'queued'` — execution lifecycle snapshot.
- `result_json jsonb`, `error_code varchar(128)`, `error_message text` — callback outcome data.
- `created_at`, `published_at`, `started_at`, `finished_at`, `updated_at` — audit and recovery timestamps.
- A `unique (task_id, attempt)` constraint and an index on `(task_id, attempt)`.
- A status check constrained to `queued`, `running`, `succeeded`, `failed`, and `canceled`.
- The existing `set_updated_at()` trigger function is reused for execution updates.

The Java module gains `GenerationTaskExecutionEntity` mapped exactly to those columns.  `GenerationTaskEntity` is not expanded with a mutable `messageId`; the execution table is the durable source of truth for message identity and history.

## Callback acceptance contract

When the callback implementation is added, it must:

1. Load the execution by callback `messageId`.
2. Confirm its `taskId` and `attempt` equal the callback values.
3. Confirm the associated task's active `attempt` is the same attempt before applying a non-terminal state transition.
4. Treat a duplicate result for the same terminal execution as idempotent.
5. Return the documented ignored result for an unknown, stale, mismatched, or superseded execution without modifying the current task.

This change intentionally creates the persistence seam only.  The current Java checkout has no callback controller or task state-transition service, so it does not introduce an incomplete controller solely to expose the table.

## Testing

Add regression tests that require the V5 migration, verify its primary key, foreign key, unique `(task_id, attempt)` constraint, immutable payload column, lifecycle columns, and supporting index.  Add entity-mapping coverage to require `GenerationTaskExecutionEntity` and verify its `messageId`, `taskId`, `attempt`, JSON snapshot/result, and timestamp mappings.

## Out of scope

- Publishing messages to RabbitMQ.
- A transactional outbox or publisher-confirm implementation.
- Worker callback controller/service implementation.
- Public API response changes.

Those later steps consume this durable execution identity rather than inventing a second identity scheme.
